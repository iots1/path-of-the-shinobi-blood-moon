# CLAUDE.md — Path of the Shinobi: Blood Moon

You are helping build an isometric ink-brush-style action game. The user is new to Blender and 3D, and speaks Thai — converse with them in Thai, explaining steps one at a time and naming exact menu/button labels.

## What the game is
- Protagonist: a ninja in a grey hood with a face covering and black kimono, two swords sheathed on the back, wielding one katana
- Look: black/white/grey ink-brush-on-paper style, with a single spot of red (the torii gate, the final combo kanji)
- 3-beat combo: 一 diagonal downward slash → 二 upward slash → 三 lunging horizontal cut (right → left, two-handed, body leaning forward, big ink-arc finisher)
- Map: a floating isometric island with a stone courtyard, a pond, cuttable bamboo, and straw training dummies

## Key files
- `client/index.html` — the entire game in one file (ES module, `three@0.160.0` via importmap from jsdelivr), divided into sections by comments `1) ART … 6) CAMERA`
- `client/legacy/ninja-dojo-2d.html` — the 2D prototype (PixiJS), kept for reference, do not edit
- `server/main.go` — Go dev server (serves the client + assets)
- `art/reference/` — reference images: `ninja-sword/` (no face covering, sword on the back), `ninja-body/` (no face covering, no sword — body/proportions only), `cloak/` (hooded — the current in-game model's source reference)
- `assets/ninja.glb` — the character: a full-body hooded model (Meshy multi-image-to-3D + rig, Git LFS), hood/cloak sculpted into the mesh (the sculpted back swords were cut out; code-built ones replace them). Bone list + mapping: `docs/BONES.md`. Inspect with `python3 tools/inspect_glb.py assets/ninja.glb`. **Not Mixamo naming** — see BONES.md before touching bone names in code.

Run with `cd server && go run .` then open http://localhost:8080

## Client architecture (know this before making changes)
- Units = meters. The character faces +Z; the character's right hand is on the -X side. Height 1.75 m.
- **Color pipeline is pinned to r128 behavior**: `THREE.ColorManagement.enabled=false`, `renderer.outputColorSpace=LinearSRGBColorSpace`, `renderer.useLegacyLights=true` (deprecated in 0.160, removed in r165 — upgrading Three.js past that means retuning light intensities). Don't flip these without comparing screenshots.
- **Two rigs.** The procedural rig (nested `THREE.Group`s in `rig`: `root → hips → spine → chest → neck → head`, legs `thighL/R → kneeL/R → ankleL/R`) is now an **invisible driver**. `applySkeleton()` poses it exactly as before, then `driveRealBones()` copies each driver's rotation delta (relative to its rest) onto the matching real bone of `assets/ninja.glb` (`BONE_MAP`, section `3b`). If the glb fails to load, the procedural body stays visible as a fallback.
  - This model's bones have **no naming prefix** (`Hips`, `Spine`, `LeftArm`, …) and the spine order is reversed vs. a typical Mixamo rig — `Spine02` is closest to the hips, `Spine` (no suffix) is closest to the neck. See `docs/BONES.md`.
  - The Armature node carries a **0.01 scale** (mesh authored in cm-like units). Two consequences: (1) quaternions must be extracted via `Matrix4.extractRotation()` first, never `Quaternion.setFromRotationMatrix()` on a matrix that still has this scale baked in — it silently produces a non-unit quaternion and the whole rig collapses; (2) a `Mesh` parented directly as a child of one of these `Bone` objects doesn't render (looks like a frustum-culling quirk) — world-space props must be positioned every frame via `matrixWorld`, never literally `bone.add(prop)`.
  - Meshy's bind pose has the legs splayed; `real.corr` straightens the legs first so `spread` etc. mean the same as on the driver. **Important:** correcting each leg segment independently (thigh and knee each rotated to point straight down on their own) leaves the skeleton geometrically straight but makes the *knee bone's own rotation* deviate far from its bind value — which this model's imperfect auto-rig skin weights render as a visible crease at the knee, even though the joint positions are correct. The fix is to apply the **same** correction quaternion to the thigh and shin (`UpLeg`/`Leg` share one `corr`), rigidly re-aiming the leg as a unit so each bone's rotation stays close to bind. The **foot is deliberately excluded** — giving it the leg's correction tips the toes down ~12° and reads as standing on tiptoe; without it the foot keeps its bind orientation (flat). If a joint ever shows a visible crease despite looking geometrically right, suspect this (check how far the bone's live rotation has drifted from `real.bind[name].q`, not just the joint positions).
  - **Ground snap** (post-pass in `applySkeleton()`): leg FK never lands the feet exactly on the floor (crouch poses sink them, straightened legs float them). After `driveRealBones()`, the lowest of the four foot contact points (`real.ground`: `Left/RightFoot`, `Left/RightToeBase` with their bind-pose heights) is compared to its bind height, `rig.hips.position.y` is shifted by the gap, and `driveRealBones()` re-runs. Sinking is always corrected; floating is only corrected in proportion to `1-.85*walkAmt`, so running keeps a flight phase. This replaced an analytic hip "lift" that over-lifted and made the character look tiptoed — don't hand-tune hip height or the crouch knee-bend formula to fix foot contact.
  - **Locomotion legs come from Meshy's clips** (`assets/anim/walk.glb` + `run.glb`, the free clips from the rig task — skeleton + clip only, in place). `loadLocoClips()` keeps only the 8 leg-bone quaternion tracks of each and self-calibrates them (planted-toe speed: walk ≈1.27 m/s, run ≈6.1 m/s — a sprint; and when the left foot is furthest forward). Both clips run on **one shared normalized phase** `loco.u` (aligned so the left foot is forward at the same u), blended walk→run by speed (`loco.b`), then slerped over the procedural legs by `walkAmt` in `driveRealBones()` — standing/attacking is fully procedural, so slashing mid-run fades the legs out in ~0.3 s. Hips, torso, arms/sword IK stay procedural; `walkPhase` is derived from `loco.u` so arm swing and torso twist stay in step. Tuning knobs at the top of section 3b: `RUN_SPEED` (4.0 m/s) and `WALK_SPEED` (1.6 m/s, while Shift is held — `keys.shift` is refreshed from `e.shiftKey` on every key event; `walkAmt` saturates at `WALK_SPEED` so walking still drives the legs fully), `RUN_LEAN` (extra forward spine lean at full run, head counter-tilts 55% of it); walk↔run blend uses ground speed (walk <2 m/s, run >3.4 m/s) and `CADENCE_BOOST` (1.2 = steps 20% quicker than the stride strictly allows; raise for faster footwork at the cost of some foot slide). Model versions + Meshy task IDs: `assets/raw/README.md`.
  - **Procedural run cycle / toe-in** (now only the fallback, and blended in at low speed): the bind pose turns the toes out ~25°. Most of the inward turn is applied as ankle Y rotation; the thigh gets only a slight knee-in twist, because twisting the thigh far also rotates the knee-bend plane and every bent knee then flicks the shin outward (bow-legged gallop). Spread narrows with `walkAmt`. Thigh swing is asymmetric (further forward than back), the stance knee flexes at mid-stance, and the spine leans forward more while moving.
  - **Running / walking carry (2026-10).** While not attacking, the pose target is `mix(IDLE, CARRY, walkAmt)`: `CARRY` holds the blade upright-forward beside the right hip (tip above the shoulder). The IDLE blade (low, across the front) was inside a swinging leg in ~60% of run frames; now the blade stays ≥18 cm from the leg bones. The sword arm swings only ±4 cm (it used to swing ±15–25 cm, which waved the blade and made the grip solver re-twist the wrist every step), and the run's hip/shoulder counter-twist was halved (hips .06, chest .09 rad). Don't solve "wrist twists while running" by locking the hand to the forearm — tried: the blade then hangs along the leg and the legs pass through it.
  - **Arm/grip continuity (don't regress).** Measured per 4 ms step (hand-vs-forearm °/s, elbow m/s) with `I.stop()` + `frame(0,4,true)`: (1) `gripPass` keeps the elbow swivel continuous — last frame's elbow (`arm.eRel`, committed by the caller) is located on the new circle, moving away costs `GRIP_TUNE.swivelHold`/°, and the result is eased (`tauSwivel`); the pole-based reference elbow itself flips when the shoulder→wrist axis swings past the pole, which made the left elbow jump ~30 cm in one step as it reached for the hilt. The left hang-IK pole is aimed at last frame's elbow while gripping. (2) The blade basis uses the smooth analytic `fall` vector, not `S.edge` (which snaps between fall and the motion direction; since the fist is locked to the blade's roll, every snap spun the wrist at ~40,000°/s). `S.edge` is still used for hit FX. (3) The off-hand grab/release turns the fist from last frame's orientation toward the grip or bind pose (`a.haPrev`), not bind→grip by `blend` (shortest-path slerp flipped when they're ~180° apart; keeping a hemisphere drifted onto a 300° path). (4) The sword is glued to the fist after the arm solve (blade = hand·K⁻¹, G = wrist + palm offset), so the hit test/trail use exactly what's drawn. Results: run/walk/stop wrist ≤~1,000°/s, no elbow jumps; slashes p95 ~2,000°/s (fast cuts), grip held through beats 1–2.
  - **Beat 3 = lunging horizontal cut (2026-10; replaces the 360° spin).** Four keys (`hit:2`): wind-up (torso wound right: hipYaw −.34 / chestYaw −.46, blade out behind the right hip `by −62`), mid-sweep (blade forward), strike end (torso unwound +.3/+.44, blade `by +66`, lean .42 — forward-leaning, only a slight crouch), follow-through; `lunge:3.4` steps the body forward during the cut; all keys keep `two:1` with the hands in front of the chest at belly height, so the off-hand never crosses the body. Faster dynamics (`hand`/`blade` 4.2 Hz, `body` 3.6 Hz). The blade sweeps ~210° (the torso gives ~90° of it). Finisher effects (`def.final`): trail lingers 700 ms (`stroke.life`) and keeps drawing 260 ms past the strike, `finisherImpact()` (ink spray fan along the cut, large floor splats, camera punch-in `S.punch`), hit-stop 120 ms, shake .30, dummies knocked 2.4× — and `hitTest` accepts targets right against the hands (`u>.04`, the normal beats need `u>.25`) because the sweep must also cut things pressed up to the character (the dummy collider keeps you ~.5 m away). `spin`/`spinHit` are no longer used by any beat (the `spin` pose parameter and its dynamics still exist).
  - **Arms vs. the torso / the free off-hand (2026-10).** `BODY` (section 3b, before `gripPass`) is the torso as an elliptic cylinder in chest-local space (half-width .15, front ≈.19 / back ≈.11, y −.55…+.2; measured from the skinned mesh) inflated by the arm radius; `swivel()` (shared by `gripPass` and the off-hand's final solve) adds `GRIP_TUNE.bodyK` per cm an elbow/upper-arm/forearm point sits inside it. Three things actually fixed "left arm through the body": (1) the **hilt is pushed radially out of the torso** before the arms are solved (right grip, left grip and pommel, with margins for the wrist sitting ~8 cm behind the palm) — with the blade pointing down/forward the pommel end, and so the left wrist, was 10–15 cm inside the chest; (2) the off-hand is solved as **one IK + swivel** for the blended wrist target, not by lerping the hang elbow and the grip elbow (that lerp cut through the chest mid-grab); (3) the off-hand **lets go when the hilt sweeps past the body's centre line at chest/belly height** (`crossL`, beat 3) instead of dragging the arm straight across the torso. The free off-hand is never a dead hang and never thrown out sideways: standing = elbow ~120° with the fist in front of the hip and the elbow tucked back (`stand`), walking/running = a runner's pump (`walkP`/`runP`, elbow ~80–115°, fist from belly-front to the hip, elbow behind the body, contralateral to the legs), elbow side from `poleFree`. (An earlier "balance" pose threw the left arm out to the side at the start of EVERY attack, before it had reached the hilt — it read as a flailing, broken arm; don't reintroduce it.) **Hysteresis trap:** the swivel search has a continuity term (`swivelHold`), and with a free arm it kept the elbow on whichever side it last happened to be — results depended on the arm's history (a flared elbow survived a whole second of idle; the 2nd `m.run()` in a page gave a 17 cm flare where the 1st gave 5 cm). The off-hand's final solve therefore scales the hold by `twoEff` (no hold when free). Run `m.run()` 2–3 times in one page when touching arm solving: the numbers shift a little (the leg-cycle phase `loco.u` carries over between scenarios) but must not jump (3× differences = a sticky solver branch). The slide along the hilt is eased (`S.sdL`), and the off-hand's orientation fades from its smoothed state onto the exact grip as `twoEff`→1 (a threshold switch caused 11–14k°/s one-step spins). `motion_check.js` measures arm-in-torso depth (run/walk ≤1 cm, combo ≤12 cm).

- **Arms are not driven by the driver rig.** 2-bone IK (`solveIK`) runs from the real `LeftArm/RightArm` positions with the real segment lengths, then `aimArm()` aims the real upper/fore-arm bones at the IK elbow/wrist (with a twist so the mesh's elbow hinges in the bend plane). - **Poses are parameters, not direct bone keyframes**: `IDLE = {hx,hy,hz (hand position in chest-local coordinates), by,el (blade direction), hipY, hipYaw, chestYaw, lean, headYaw, spin, spread, two, eye, glint}`
- `COMBO[]` = a list of timelines `keys:[[time ms, pose, ease], …]` (any number of keys; eases `out`/`in`/`lin`/`snap`/`io`) plus `hit` (index of the strike key, default 1 — the lunge and trail run keys[0]→keys[hit]; the hit test runs keys[0]→last key+40), `impactMin`, `chain` (the time window to chain into the next combo hit), `end`
- Every parameter passes through `SOD` (second-order dynamics) before use; the (f, ζ, r) values differ per group (hand/blade/body/spin). This is what keeps poses from looking mechanical — **do not replace it with plain lerp**.
- The "hit" beat is detected from the sword tip's velocity starting to decrease, not from a fixed time (`maxSp`, `decel`). That's what triggers hit-stop, camera shake, and the combo kanji.
- Hit detection uses the distance from the blade's line segment (wrist→tip) to the target's axis on the XZ plane (`hitTest`)
- The loop uses a fixed 4ms substep (`step(T)`). The camera is orthographic isometric (yaw 45°, pitch 35.26°), rotating 90° at a time with Q/E.

## Blender
See `docs/BLENDER_MCP.md` — uses blender-mcp (configured in `.mcp.json`). The user needs to have Blender open and click Connect first. If the blender tools aren't visible, ask the user to check that step.

### Pitfalls when editing `ninja.glb` in Blender (all hit in practice)
- **Restart `claude` after approving the MCP server** (`claude --continue` keeps the conversation) — the `mcp__blender__*` tools don't appear in a session that started before approval, even though `claude mcp list` shows ✔ Connected.
- **glTF import oddities**: the Armature is scaled 0.01 and `char1` vertex coordinates are in cm (world = local × 0.01); the bones are drawn as huge octahedra and `Icosphere` (collection `glTF_not_exported`) is the importer's bone shape — don't delete it. The huge bone shapes + Icosphere swallow the `look` camera (grey/blank screenshots): hide `Armature` and `Icosphere` before `look`, and to frame the head use an Empty at the head as `target` with a small `distance`. `get_scene_info` lists only top-level objects, so `char1` (child of Armature) looks "missing" — it isn't.
- **Check `char1`'s rotation before exporting.** A fresh import has `rotation_quaternion = (1,0,0,0)`; an accidental drag/rotate in the viewport (it happened twice: ~7° about X, later ~141° about Z while trying to see the back — use Ctrl+Numpad1 for a back view instead) silently tilts the exported mesh. Compare the exported `POSITION` accessor with the known-good bounds `min [-0.813, 0, -0.279]`, `max [0.813, 1.75, 0.279]`; also `Armature` and `char1` `matrix_world` must be pure 0.01 scale. Don't leave Blender in Edit Armature mode either.
- **The imported Armature carries an action** (`Armature|clip0|baselayer`) that re-evaluates the pose on frame changes — reset pose-bone quaternions/locations (and return to Object mode) before exporting; pose a test, then reset.
- **Export recipe** that round-trips cleanly (identical node/bone structure, 1 material, 3 PNG images, `TANGENT` kept): select `Armature` + `char1`, `bpy.ops.export_scene.gltf(filepath=…, export_format='GLB', use_selection=True, export_skins=True, export_animations=False, export_tangents=True)`. The baked rest clip is dropped on purpose (the game only reads animations from `assets/anim/walk.glb` and `run.glb`). Verify with `python3 tools/inspect_glb.py`. Keep a copy of the previous glb (it's also in git LFS) — `git checkout assets/ninja.glb` restores it.
- **Adding geometry to `char1`** (the eyes): append to the same mesh with the same material slot, weight 100% to a bone via the deform layer, and give it **non-degenerate UVs** — if every vertex of a part shares one UV the exporter writes a zero `TANGENT`, and three.js turns the normal-mapped surface black (NaN): the first eye plates were invisible in-game for exactly this reason while looking fine in Blender. Anything you paint into the atlas corner must also be neutral in `normal` (black decodes to a garbage normal) and `metallic_roughness`. Verify that edited texture pixels survive the export by extracting the PNGs from the exported glb. Don't add a second mesh/material (see the `skinned` note in follow-ups). The face front is at world y≈-0.19 (mesh-local ≈-18.9 cm) and strongly curved (drops ~2.7 cm between x=0 and x=±5); the hood brim's lower edge arches over it at z≈164 cm.
- **Vertex order / groups**: char1 is now the original Meshy mesh minus the back swords and the cut-out upper-back zone, then the fists (`_fists`, 3,566), then the painted face plate (`_eyes`, 2,665), then the cloak patches (`_patch`, ~1,800 incl. small hole fills), 30,833 total in Blender (33,047 in the glb after UV-seam splits). Indices shift whenever a part is rebuilt — always select by the `_eyes` / `_fists` / `_patch` vertex groups (they are not bones, so the exporter ignores them for skinning). The fists use a 32×32 glove tile at pixel (108,80) of `texture_0` (value 22/255; a black tile lifts to ~0.07 in the game, the same as the outline, so fingers wouldn't read) — a Meshy re-export or texture repack loses it and the face strip. The old eye atlas tiles in the bottom-left corner are now unused. Rollback sources (unsaved .blend, fake-user datablocks): mesh `mesh_before_swords` (before the back swords were cut), `mesh_before_backfix` (swords cut, before the big back patch), `mesh_before_face` + image `texture_0_before_face` (before the face plate), mesh `orig_mesh_keep` (original Meshy), or git.
- **Re-weighting by connected island**: vertex-group `remove()` while iterating `v.groups` leaves the old weights in place; use a bmesh deform layer (`v[dl].clear(); v[dl][idx]=1.0`). Meshy meshes are split at UV seams, so coincident duplicate vertices exist — weight them together or the seam tears.
