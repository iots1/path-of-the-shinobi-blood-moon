# Character asset: the no-hood swap (2026-10-19) + standing / carry / sword-arm tuning

> Moved verbatim out of `CLAUDE.md` on 2026-10-22 (it was over the size limit). The asset facts of the current Meshy no-hood model and the first tuning passes on it (idle blade angle, `GRIP_CFG.R.phi`, `poleR`, `CARRY`, sword-arm swing, right-shoulder balance, standing pose vs. the reference). Later hand/grip, run and face work is in the sibling notes.

### Current model (2026-10-19 no-hood swap — read this first; the 2026-10-18 section right below now describes the PREVIOUS model)
Source: `blender-ninja/new_ninja_no_hood/Meshy_AI_Unmasked_Male_Ninja_T_All_Animations.glb` (18,887-tri body, Mixamo rig, 4096² base-colour + 4096² normal + 4096² metallic/roughness, own `Walking`/`Running` clips) copied unchanged to `assets/ninja.glb` — nothing edited in Blender. Backup of the previous (hooded/masked) `ninja.glb` + that day's `client/index.html`/`motion_check.js`: `assets/raw/backup-hood-v2-2026-10-19/`.
- **Bone names/units are compatible with the existing loader, no `canonBone`/`BONE_MAP` changes needed.** Same Mixamo naming (`mixamorig:Hips`, `Spine/Spine1/Spine2`, `Neck`, `Left/RightShoulder`, `…Arm/ForeArm/Hand`, `…UpLeg/Leg/Foot/ToeBase`), same convention (metres, no 0.01 Armature scale, root node has no scale either). Every bone name `BONE_MAP`/`real.corr`/`real.ground`/`real.shAx`/`BACK_SWORDS` reference exists in this rig too.
- **(Both hands superseded 2026-10-19/20 — see "Right-hand finger rig" and "Left-hand finger rig" at the end of this section.) No finger bones** (28 joints total vs. the previous model's 66, as originally shipped) — just one end bone per hand (`LeftHandMiddle4`/`RightHandMiddle4`, used here only to confirm the hand-local finger axis is still `+Y`, matching `GRIP_CFG`'s assumption). `prepFingers()` already skips any finger whose 3 joint bones aren't found (`if(bs.some(b=>!b)) continue`), so it returns an empty list and `setFingers()`/`FIST` become no-ops — no crash, but the hand never curls into a fist; it's whatever shape is baked into this mesh's hand. Also has an extra `headfront` bone (unused by any code, harmless).
- **Arm reach is ≈0.457 m (L: .218+.239, R: .204+.253), almost exactly `ARM_REF`=.456** — unlike the 2026-10-18 model (reach .389, needed the whole "rescale every key" pass documented below), this rig needed **no hand-target rescaling**: `real.armK` computes to 1, the existing (2026-10-18-authored) `IDLE`/`COMBO`/`ATTACK2`/`DUAL`/`ISSEN` keys all land inside reach as-is.
- **Base-colour image index bug, fixed.** `embeddedImageTexture()` (the workaround for GLTFLoader's racy texture resolution on this glb's large embedded PNGs — see the note below) hardcoded image index 0 as the base-colour texture; that happened to be true for the 2026-10-18 model but this export puts the **normal map** at image 0 and base-colour at image 1 (`materials[0].pbrMetallicRoughness.baseColorTexture.index` → `textures[1].source` → image 1). Using the hardcoded 0 rendered the whole character pale blue-grey (the normal map's tangent-space colours used as albedo). Fix: read the base-colour image index from `gltf.parser.json` instead of hardcoding it — `loadNinja()`, right before the `embeddedImageTexture()` call. Re-check this on any future model swap; don't assume image order.
- **Known issue carried over, same class as the 2026-10-18 model's documented grip-flicker limitation (see "Side effect, accepted as a known issue" below), now also hitting beat 2 二.** `m.run()` fails `combo (from a run) two-hand grip` (min ≈0.00) and sometimes `combo (standing)`/`finisher L` (the pre-existing first-attack-after-reload flake). Measured with a temporary debug hook on `S.gripOn`/`q2.bend`/`crossL`: during beat 2's sweep (≈t+24–184 ms into that beat) `q2.bend` crosses 148–151° and `crossL` crosses below −.12, tripping the same release/re-grip hysteresis documented for beats 1/3 on the previous model — just landing on a different beat because this rig's different upper-arm/forearm split (more even, vs. the old model's short-upper-arm/long-forearm) changes where the swivel search's bend crosses the threshold. Confirmed with `m.sheet({mode:'combo'})` that this is a brief (~20–40 ms) sub-sampling blip, not a visibly broken pose — every sampled frame in the contact sheet reads `2h1.0` through the whole combo. Not re-choreographed (same conclusion as the earlier investigation: fixing it for real means re-timing the beat or a global swivel-branch control, not a quick key tweak) — left as a known/accepted limitation like its predecessor.
- **Back swords (code-built, `BACK_SWORDS` in `loadNinja()`) overlap on this body.** The two points were measured for the PREVIOUS (cloaked) model's back surface; on this slimmer, hoodless body the two sword placements land only ~7–8 cm apart world-space, so the empty saya mostly hides behind the full sheathed sword instead of sitting beside it. Visually acceptable from the default gameplay camera/zoom but should be re-measured (ray-cast from behind in Blender against this mesh) if it's ever looked at closely.
- **Eye glow (`real.eyeLocal`/`real.eyeRot`) not re-measured for this head** — kept the previous model's guessed values. Not visible in practice (`eye` pose parameter defaults off, same as the previous model), so harmless unless something turns the glow back on; re-measure against this head/face first if so.
- **Material/outline settings kept as-is and look right without retuning**: base-colour mean ≈21/255 (similar to the previous model's ≈28/255), so the existing `bodyGrad` ramp + albedo gamma lift (`0.07+0.93*pow(c,0.42)`) and `.008` outline thickness all still read correctly (checked in-browser at gameplay zoom and in contact sheets) — no self-intersecting outline gouge observed on this mesh's shoulders.
- Verified: `m.run()` — locomotion (run/walk/stop wrist, elbow, blade↔leg clearance, arms-inside-torso, free-arm flare/bend) all PASS; only the two-hand-grip flicker above FAILs, matching the previous model's accepted class of issue. `m.sheet({mode:'combo'|'issen'|'run'|'idle'})` screenshots confirm clean two-handed grip through the actual slash frames, a natural run cycle using this glb's own clips, and the face/outfit/outline rendering correctly (no hood, as intended).
- **Idle blade angle re-tuned (2026-10-19, same day).** The `IDLE` stance was carried over unchanged from the previous model (`by:60, el:-38` — blade ~51° off vertical), which on this rig read as the sword jutting out sideways from the hip instead of hanging down, compared to the reference `art/reference/new_ninja_katana/ninja_katana_2_front.jpeg` (blade mostly vertical, close alongside the leg, slight forward lean). First change: `by:40, el:-60` (~29° off vertical) — fixed the silhouette but, per a side-view comparison against the same reference, raised the physical wrist bend to ~50° (visible kink between forearm and hilt). Superseded by the `GRIP_CFG.R.phi` fix below.
- **Wrist-bend/blade-angle trade-off fixed by raising `GRIP_CFG.R.phi` (2026-10-19, same day) — read this before changing `IDLE.by/el` or any `GRIP_CFG` value again.** Numerically scanned (by, el) at the inherited `phi:30`: for this hand mesh, every combination traded wrist bend against blade-vertical-angle directly (e.g. by40/el-60 → bend 52°/vert 29°; by110/el-45 → bend 0.5°/vert 46° but the blade then points backward past vertical, cos(by)<0) — **`phi` itself was still the old model's value**, never re-measured for this mesh, so it was scanned too: raising it shifts where the low-bend zone falls in (by,el)-space. `phi:75` lets `by:35/el:-55` reach bend≈9° (was ≈50° at phi:30) while the blade still hangs down-forward (~34° off vertical, not pushed backward) — matches both the front-view silhouette reference and a side-view reference showing a straight forearm→hilt line. `phi` is global for the right hand (every pose's `qBR` uses the same `GRIP_CFG.R.K`, not just `IDLE`) — re-verified with `m.run()`/`m.sheet()` across idle, the 3-beat combo, K (thrust), K K (dual) and L (issen): dual/thrust hits, finisher delayed-hit, and "hits on all 3 beats" all still PASS; two-hand grip is unaffected or improved (finisher L's grip metric went 0.67→0.90; the pre-existing beat-flicker FAILs on `combo (standing)`/`combo (from a run)` are unchanged, not new). `GRIP_CFG.L.phi` (the off-hand/dual-sword hand) was left at 30 — not re-scanned, since nothing flagged it and the off-hand's own grip metrics stayed healthy. If the off-hand's grip ever looks mismatched, re-scan `L.phi` the same way (sweep `by/el/phi`, force `arm.?.eRel=null` before each measurement to avoid landing on a stale swivel branch, measure both the physical wrist-bend angle and the blade's angle off vertical).
- **Sword-hand elbow flare reduced via `poleR` (2026-10-19, same day) — this is a 3rd axis of the same by/el/phi trade-off above, not a separate bug.** Fixing the wrist bend (previous bullet) left the idle elbow ~10 cm outboard of the shoulder (flagged against a front-view skeleton overlay vs. a front reference showing the elbow tucked close to the torso). Measured that `GRIP_TUNE.swivelBias`/`swivelHold` couldn't pull it in — at a fresh `arm.eRel=null`, the swivel search already lands within a few degrees of the fixed-pole elbow (`poleR` in the pose function, section 4), so the outboard position IS where physical wrist bend is minimized for this by/el/phi, and biasing harder toward the pole doesn't change what the pole itself points at. Rescanned `poleR` jointly with by/el/phi (same method: force `arm.R.eRel=null`, settle ~1.6 s, measure bend + chest-local elbow-vs-shoulder offset at each candidate): `poleR` chest-local-pre-rotation `(-1,-.5,-.6)` → `(-.5,-.95,-.35)` trades idle wrist bend ~9°→~16° for elbow flare ~10cm→~7cm. `poleR` is also global to the right hand (used by every pose, not just `IDLE`) — re-verified the same way as the `phi` change: `m.run()` only the 2 pre-existing beat-flicker FAILs, `m.sheet({mode:'combo'})` still reads clean two-handed grips through the cut frames.
- **Running/walking carry (`CARRY`) re-tuned (2026-10-19, same day) — a separate pose from `IDLE`, broken by neither of the two fixes above but flagged in the same round of reference comparisons.** `CARRY`'s blade angle (`by:-15, el:55`, unchanged since before the no-hood swap) pointed the tip ~56 cm forward-up of the chest on this rig (measured at the grip point + 0.82 m along the blade) — combined with the run's forward lean this read as the sword (and the arm with it) thrust out in front while running, instead of carried, per a side-view running reference (`art/reference/ninja-no-hood/...`) showing the elbow bent BACK with the hand at the hip. Flipping the blade's yaw to point the tip backward instead (`by:165, el:-10`) fixed the arm/elbow direction but put the tip through the swinging legs' own height band — `m.run()`'s blade↔leg clearance dropped to ~1 cm (limit 10 cm); raising the grip high enough to clear it (tried up to `hy:.35`) put the hand up near the face instead, worse than the original problem. Settled on `by:140, el:85` — same backward lean as the by:165 attempt, but mostly a vertical carry like the original fix (at `el:85`, `cos(el)` is small enough that `by` barely matters) instead of near-horizontal: the elbow still reads as bent back with the hand at the hip, the blade trails up and back over the shoulder instead of forward, and it clears the legs by ~11-18 cm measured across several **fresh page loads** (not just repeated `m.run()` calls in one session — the run/walk START is history-sensitive the same way the grip system's first-attack-after-reload flake is documented to be elsewhere in this file: `by:140, el:55` and `el:65` each passed a warm-session `m.run()` but intermittently failed (~0.08-0.10 m) on a cold reload, because at low `walkAmt` the pose is a blend with `IDLE`'s forward-pointing blade that can pass through a worse angle than either endpoint). **Always reload the page a few times when tuning `CARRY`, not just re-run `m.run()` in the same tab.** Verified: `m.sheet({mode:'run'})` shows a clean run cycle, elbow tucked near the hip throughout, no leg clipping.
- **Sword arm now swings during walk/run, matching the off-hand's existing pump (2026-10-19, same day) — requested as a first pass while the hand/finger rig is reworked in a separate session, before that lands.** The sword arm used to move only ±4 cm (`Math.sin(ph)*.04*w` on `hz`) specifically to avoid waving the blade/re-twisting the grip every step (see the "Arm/grip continuity" note above) — which, combined with the `CARRY` fixes above, still read as the arm barely moving while the off-hand visibly pumped. It now reuses the off-hand's own per-axis swing shape (`SWING_Y`/`SWING_Z` in the pose function, blended walk→run the same way the off-hand's `walkP`/`runP` are) as a delta on top of `CARRY`/`IDLE`'s own `hx,hy,hz`, mirrored in phase (`uR=1-u`, since the right arm leads with the left leg) rather than jumping to an absolute target like the off-hand does (the sword hand has an authored base pose to swing around; the off-hand doesn't). Verified with `m.run()` across several fresh loads: run→stop wrist peak rose from ~800-1300°/s to ~2000-2400°/s (limit 2800 — closer to the ceiling than before, re-check this limit if the swing amplitude is ever increased further) but nothing failed, and `combo (from a run)`'s elbow-jump/wrist-peak (the transition from this swinging arm into an attack) are unchanged from before this change — no new spikes. `m.sheet({mode:'run'|'walk'})` shows a natural pump, contralateral to the off-hand as intended. Not re-verified: how this interacts with a right hand that actually curls its fingers around the grip (the other session's finger rig) — if the bigger swing reads as wrong once that's in, the fix is more likely in how hard the swing amplitude is clamped here than in the fingers.

- **Right shoulder/arm balance at idle (2026-10-20) — user comparison image (right shoulder looked higher/shrugged, elbow tucked, hand inboard of the left).** Code-only, no Blender/skin-weight change (the bind skeleton is symmetric: both `Arm` joints at y 1.376; the asymmetry is the mesh, see the shoulder-mesh note). New `SHOULDER.dropR` (.08 rad, ≈1.2 cm lower right shoulder, applied ×(1−carry) so running/carry is unchanged; scan: .07→1.0 cm, .15→2.1 cm) rolls only the RIGHT clavicle further down than `drop`. `IDLE` hx −.22→−.27, hy −.42→−.44 moves the sword hand ~5 cm outward and 2 cm lower, so the elbow flares like the left one (elbow-out 4.4 cm vs left 4.7; was 4.2 vs 6.9 hand-out gap) — blade angle/`GRIP_CFG` untouched, settled wrist bend 12°→11°. Right elbow stays ≈163° (≈17° bend). Arm bone lengths can't match exactly (R .204+.253 vs L .218+.239 — mesh/rig, not touched). `m.run()` all PASS on fresh reloads (combo grip min 0.88, hits 1,2,3). **Gotcha: the browser caches `client/index.html` too — after editing, load `/?v=N` (a plain reload ran the OLD code and made `dropR` look like it did nothing).**

- **Standing pose matched to `art/reference/new_ninja_katana` (2026-10-21).** `/debug/run-overlay.html` has two more views, **ยืน · หน้า / ยืน · ข้าง** (`ninja_katana_2_front` / `ninja_katana_side_2`, copied to `assets/reference/ninja-stand-*.jpeg`): the character stands still, the reference keeps its own aspect (`fitRef()`), scale = neck → mid-ankle, and `window.__standErr` holds every joint's offset from the reference in cm (landmarks in `REFS.standFront/standSide`, read off a 50 px grid; the reference's shoulders sit ~7 cm wider because of the bulky costume). Change: `IDLE` hz .05 → −.08, hx −.27 → −.31 — the sword arm now hangs straight down at the side with the hand beside the hip (wrist 14 → 2.6 cm off the side reference, 7.4 → 3.5 cm off the front); blade untouched (forward, ~32° down, on top of the side reference's blade). **The user explicitly wants the blade forward, not across the body** — the front reference's diagonal blade is not to be copied. `m.run()` 110/110 (watch: combo "arms inside torso" now 11.1 cm at 1680 ms, limit 12).
