# Blender pitfalls when editing `ninja.glb`

> Moved verbatim out of `CLAUDE.md` on 2026-10-22 (it was over the size limit). See also `docs/BLENDER_MCP.md`. Some entries refer to the older hooded model (`char1`, cm units, 0.01 armature scale); the no-hood model is in metres with no armature scale.

### Blender
See `docs/BLENDER_MCP.md` — uses blender-mcp (configured in `.mcp.json`). The user needs to have Blender open and click Connect first. If the blender tools aren't visible, ask the user to check that step.

### Pitfalls when editing `ninja.glb` in Blender (all hit in practice)
- **Restart `claude` after approving the MCP server** (`claude --continue` keeps the conversation) — the `mcp__blender__*` tools don't appear in a session that started before approval, even though `claude mcp list` shows ✔ Connected.
- **glTF import oddities**: the Armature is scaled 0.01 and `char1` vertex coordinates are in cm (world = local × 0.01); the bones are drawn as huge octahedra and `Icosphere` (collection `glTF_not_exported`) is the importer's bone shape — don't delete it. The huge bone shapes + Icosphere swallow the `look` camera (grey/blank screenshots): hide `Armature` and `Icosphere` before `look`, and to frame the head use an Empty at the head as `target` with a small `distance`. `get_scene_info` lists only top-level objects, so `char1` (child of Armature) looks "missing" — it isn't.
- **Check `char1`'s rotation before exporting.** A fresh import has `rotation_quaternion = (1,0,0,0)`; an accidental drag/rotate in the viewport (it happened twice: ~7° about X, later ~141° and ~178° about Z while trying to see the back — use Ctrl+Numpad1 for a back view instead) silently tilts the exported mesh. Compare the exported `POSITION` accessor with the known-good bounds `min [-0.813, 0, -0.279]`, `max [0.813, 1.75, 0.279]`; also `Armature` and `char1` `matrix_world` must be pure 0.01 scale. Don't leave Blender in Edit Armature mode either.
- **The imported Armature carries an action** (`Armature|clip0|baselayer`) that re-evaluates the pose on frame changes — reset pose-bone quaternions/locations (and return to Object mode) before exporting; pose a test, then reset.
- **Export recipe** that round-trips cleanly (identical node/bone structure, 1 material, 3 PNG images, `TANGENT` kept): select `Armature` + `char1`, `bpy.ops.export_scene.gltf(filepath=…, export_format='GLB', use_selection=True, export_skins=True, export_animations=False, export_tangents=True)`. The baked rest clip is dropped on purpose (the game reads animations from the `Walking`/`Running` clips in the glb itself; for the PREVIOUS model it was `assets/anim/walk.glb` and `run.glb`). Verify with `python3 tools/inspect_glb.py`. Keep a copy of the previous glb (it's also in git LFS) — `git checkout assets/ninja.glb` restores it.
- **Adding geometry to `char1`** (the eyes): append to the same mesh with the same material slot, weight 100% to a bone via the deform layer, and give it **non-degenerate UVs** — if every vertex of a part shares one UV the exporter writes a zero `TANGENT`, and three.js turns the normal-mapped surface black (NaN): the first eye plates were invisible in-game for exactly this reason while looking fine in Blender. Anything you paint into the atlas corner must also be neutral in `normal` (black decodes to a garbage normal) and `metallic_roughness`. Verify that edited texture pixels survive the export by extracting the PNGs from the exported glb. Don't add a second mesh/material (see the `skinned` note in follow-ups). The face front is at world y≈-0.19 (mesh-local ≈-18.9 cm) and strongly curved (drops ~2.7 cm between x=0 and x=±5); the hood brim's lower edge arches over it at z≈164 cm.
- **Vertex order / groups**: char1 is `mesh_before_backfix`: the original Meshy mesh minus the back swords, then the fists (`_fists`, 3,566), the painted face plate (`_eyes`, 2,665) and a few early hole patches (`_patch`), 30,558 total in Blender (32,603 in the glb after UV-seam splits). Bmesh gotchas from the cape attempt: new vertices reuse the slots of deleted ones (so an appended part's indices are not contiguous — map by position with a KD-tree), and a `v.index` taken after `bmesh.ops.delete` is stale until `index_update()` (keep BMVert references; a stale index once re-weighted the wrong vertices → spikes when the arms moved). Indices shift whenever a part is rebuilt — always select by the `_eyes` / `_fists` / `_patch` / `_cape` vertex groups (they are not bones, so the exporter ignores them for skinning). The fists use a 32×32 glove tile at pixel (108,80) of `texture_0` (value 22/255; a black tile lifts to ~0.07 in the game, the same as the outline, so fingers wouldn't read) — a Meshy re-export or texture repack loses it and the face strip. The old eye atlas tiles in the bottom-left corner are now unused. Rollback sources (unsaved .blend, fake-user datablocks): mesh `mesh_before_swords` (before the back swords were cut), `mesh_before_backfix` (swords cut, before the big back patch), `mesh_before_folds` (first big patch, before the sheet), `mesh_before_face` + image `texture_0_before_face` (before the face plate), `mesh_before_cape` (the last `_patch` sheet version, 34,168-vert glb), `mesh_cape_generated` (the rejected generated cape; its painted tile at `texture_0` px (640,300) was reverted — images `*_before_cape` hold the unpainted textures, which are the current ones), mesh `orig_mesh_keep` (original Meshy), or git.
- **If the `mcp__blender__*` tools are missing but Blender is open with the addon connected**, the addon still listens on `localhost:9876`; send it JSON directly (`{"type":"execute_code","params":{"code":…}}`, `{"type":"get_viewport_screenshot","params":{"filepath":…,"max_size":…}}`) from a small Python socket client.
- **Re-weighting by connected island**: vertex-group `remove()` while iterating `v.groups` leaves the old weights in place; use a bmesh deform layer (`v[dl].clear(); v[dl][idx]=1.0`). Meshy meshes are split at UV seams, so coincident duplicate vertices exist — weight them together or the seam tears.
